# 学习导读

## 1. CPU 是如何进入 Rust 的

UEFI / BIOS 启动 Limine，Limine 读取配置和 ELF，建立映射、准备栈、填充请求响应，最后跳到 ELF 的入口 `_start`。UEFI 路径在进入内核前退出 Boot Services；内核不能继续调用这些固件服务。

`#![no_std]` 去掉依赖操作系统的标准库，但保留 `core` 的基本类型和格式化功能。`#![no_main]` 去掉宿主应用的 main 启动约定；`#[unsafe(no_mangle)]` 保留 `_start` 的符号名。`extern "C"` 指定 ABI，`-> !` 表示入口永不返回。

引导器已提供至少 64 KiB 的栈。普通 Rust 函数可能在你的第一句源代码前生成函数序言；在函数内部手工改 `rsp` 会破坏编译器对栈布局的假设，因此删除了旧版这段操作。

## 2. ELF 文件与内存

| 区域 | 内容 | 访问权限 |
| --- | --- | --- |
| `.text` | 机器指令 | 读 / 执行 |
| `.rodata` | 常量与字符串 | 只读 |
| `.requests` | 引导请求及响应指针 | 读 / 写 |
| `.data` | 有非零初值的变量 | 读 / 写 |
| `.bss` | 初始为零的变量 | 读 / 写 |

`.requests` 与 `.data` 共用一个 RW 装载段，不同权限的段从新的 4 KiB 页面开始。不能为了缩小几个字节让只读与可写段挤到同一页：Limine 会拒绝该 ELF。

`.bss` 在 ELF 中主要记录“需要多少内存”，不保存一大串零；引导器负责清零。自检使用真实的 volatile 读写，防止编译器把检查变成常量 true。

## 3. 为什么 Rust 里仍有 unsafe

Rust 无法自动证明“某个整数端口属于 UART”“引导器返回的指针指向映射好的显存”。这些硬件边界需要 `unsafe`。代码将它集中在协议访问、端口 I/O 和显存写入处，注释列明可信条件。

`repr(C)` 固定协议结构布局；`UnsafeCell` 表示引导器会从外部修改响应字段；`read_volatile` / `write_volatile` 要求编译器保留内存访问。volatile 不等于线程安全，也不能修复无效指针。

本阶段的单 CPU、关中断、保留引导器内存是这些安全条件的一部分。将来引入多核、中断或内存回收时，必须重新审查它们。

## 4. 屏幕不是终端程序

`screen.rs` 把字形的点直接写入帧缓冲地址，写入后由显示硬件显示。`pitch` 是一行实际占用的字节数，不一定等于宽度乘像素大小；RGB 掩码也可能不同，因此必须检查并转换。

字库只有拉丁字母、数字和少量标点，小写按大写显示。中文注释留在源码中，不引入运行时中文字体。屏幕没有窗口系统、光标或输入功能。

串口则是另一条输出通道。QEMU 将虚拟 COM1 转成日志文件；Mac 屏幕不依赖 COM1。串口等待有上限，设备缺失不会卡死启动。

## 5. 为什么还需要 runtime.rs

即使源代码没有手写 memcpy，编译器也可能为结构体复制生成该调用。普通程序由 libc 提供这些符号，裸机必须自行满足。未引用的函数由链接器移除；短小的逐字节实现便于检查。

## 6. 暂时停在哪里

输出后执行 `cli; hlt`。未安装中断描述符表前不能执行 `sti`；因此键盘按键不会唤醒一个已实现的输入循环。当前仍是启动里程碑，而非能运行用户程序的完整系统。

`USABLE RAM` 是引导时内存地图里的可用总量，不是内核占用量。ELF 装载页也不包含引导器保留内存、栈、页表和显存，不能把它当作整机最低内存需求。
